# Tracker design notes

For contributors. The user-facing behaviour is in
[the tracker integration](../integrations/tracker.md); this page records how
the contract is kept and why.

## Principles

- **Derived, not stored.** Views, columns, Status options and their IDs are read
  live on every run and never stored, so a renamed column surfaces as an error
  instead of silently moving a card. Base branch and pull request come from Git
  and GitHub. There is no per-repository column override table: a board that
  does not say what its columns mean is fixed in the tracker. Synonyms (Vikunja's
  `To-Do`/`Doing`, GitHub's `Todo`) are not runtime aliases. Vikunja preparation
  proposes meaning from metadata, obtains user confirmation and executes a
  snapshot-bound temporary plan; GitHub init retains its own option planning.
- **Comments are a human journal.** Nothing machine-readable lives in one.
  Content the coordinator writes follows the resolved tracker language
  (`workflow.tracker_language`, then `workflow.language`, then the task's own
  language). New tasks without a configured language use the user's interaction
  language. Fixed diagnostic comments generated by agent-box may be English.
- **Roles.** The coordinator owns requirements, lifecycle, assignees,
  relations, progress comments and checkboxes; Plan sync may also update
  descriptions and journal comments in its scope. Checkboxes record evidenced
  progress, never review acceptance. Workers change project files and answer;
  reviewers and scouts only read. This is a contract, not credential isolation,
  and it is the same for a native subagent and a managed CLI run.
- **Scope.** A recursive binding makes every project under the root mutable;
  projects outside it stay readable, and any readable task reads its state from
  its own project's board.

## References and search

- `resolve` selects by visible number (`21` or `"#21"`), exact title or a task
  URL of the configured tracker, across the binding (children included when
  recursive). Vikunja numbers use `GET /api/v2/projects/{project}/tasks/by-index/{index}`
  per scoped project; only a missing-task response counts as absence, other
  errors stop resolution. Duplicates report project, number, title and URL for
  a user choice. `--project` narrows to one project inside the binding;
  `--title` treats a numeric reference as a title. No fallback to description
  text or global IDs; URLs outside scope are never redirected to adopted copies.
- `get` applies the same rules and also accepts a canonical ID. When a bare
  number is both a canonical ID in the binding and another task's visible
  number, it refuses and asks for `"#21"` or the URL. A canonical ID outside the
  binding still reads when no visible number matches. On GitHub the issue
  number is the canonical ID, so a bare number has one reading.
- Search returns compact summaries of open tasks, including `Unknown`. Vikunja
  filters completion, scope and query on the server, all result pages are read,
  and cards mapped to Done are excluded before output. A substring match only
  finds candidates; it never establishes the user's intended task.
  `--exclude-label` filters after all pages are read: it limits agent context,
  not API traffic.

## Writes

- **No automatic retries.** Reads report network failures as `transport`. A
  lost write reply, gateway failure or invalid success response is
  `unknown-outcome` with `retryable: false`. Authentication and revision
  conflicts keep their categories. `retryable` describes the failed request;
  earlier writes in the same command may have completed.
- **Optimistic checks are not compare-and-swap.** The adapter rereads and
  compares a task before editing and returns a conflict on change. Vikunja
  returns ETags on GET but the tested version ignores `If-Match` on PATCH, so
  nothing closes the race between the last read and the write.
- **Checklist revisions** are that same task revision, compared client-side
  before `check` writes every named item at once. The revision belongs to the
  whole task, so a journal comment moves it too.
- **Claims** check status, dependencies and assignees, assign the user, move to
  In progress and reread. A local file lock serializes local claims;
  assignment plus column movement is not an atomic distributed lock.
  Same-user In progress tasks need a deliberate `--resume`.
- **Closing unimplemented work.** `state ... Done --reason` judges every named
  task before moving any. Origin itself is asked for `ab/<id>-` branches,
  because another checkout can create or advance one and `refs/remotes/*` is
  only as fresh as the last fetch; a commit origin reports that this checkout
  never fetched is left unjudged, and the refusal asks for a fetch.

## Vikunja

- **Board preparation.** `board init` reads metadata only; an explicit five-state
  `--mapping` builds a plan and `--plan [--apply]` previews/applies that exact plan.
  Names are interpreted by the agent/user, never by an alias dictionary in the
  executor. A changed board refuses writes; a fully achieved result is a no-op.
  Lifecycle columns are ordered first, followed by retained columns in prior
  relative order. Bucket updates use v2 PUT with title, position and preserved
  limit; view updates PATCH only default/done IDs. No task moves, merges or column
  deletions occur. Optimistic inspection is not an atomic remote lock. Initial
  discovery does not fetch cards; only an explicit optional scout sample reads one
  bucket-filtered task page, without comment expansions. The view's done-bucket
  designation affects subsequent done synchronization, not historical task flags.
  API contract: [v2 OpenAPI](https://try.vikunja.io/api/v2/openapi.json), checked
  2026-10-21; fixtures do not establish live acceptance of a target instance.

- **Move.** A parent and its subtasks share one project, so `move` takes whole
  subtrees and refuses a subtask without its parent. The task keeps ID,
  relations, labels, comments, priority and assignees (checked afterwards).
  Vikunja drops a moved card into the target's default column and ignores a
  column sent with the project change, so the earlier state is restored by a
  second write; between the two writes that state exists only in workflow
  state, which records it first. A rerun of the same command finishes an
  interrupted move, and other moves wait for it. Neither `task-fields` nor
  `bulk-update` accepts `project_id`.
- **Delete project.** Vikunja deletes a project's tasks and children with it
  and has no undo, and its delete is unconditional. The command therefore
  archives the project (which refuses new tasks, moved-in tasks and children),
  checks it is still empty, and only then deletes it; a refusal unarchives it.
  It takes the move lock so it cannot interleave with a move or a cutover.
- **Import.** Rows are linked to created tasks only by a local checkpoint,
  separated by server and target ID; nothing is written into task bodies, and a
  title already in the target project is refused rather than reused. Plan IDs
  link rows within one file; existing tasks are referenced by tracker ID.
- **Container URLs.** Loopback addresses become `host.containers.internal`. A
  DNS name resolving to the host keeps its URL for TLS and virtual hosting and
  gets a Podman host mapping. Remote URLs stay unchanged.

## Vikunja adoption

- **Receipt.** Records repository and server, source and new project IDs,
  intended names, the previous binding and the exact intentional internal
  relation removals. It holds no tracker snapshot or lifecycle. A staging
  `relation ... --remove` records the intent before the API call, so retries
  are safe and only that edge is excluded from preservation checks; adding it
  back clears the exception first. Other missing internal edges block cutover.
- **Clone.** Vikunja v2.5.0's `POST /api/v2/projects/{id}/duplicate` runs once
  per project with `duplicate_shares: true` and the new parent. Tasks are
  matched by their preserved per-project index; missing assignments are added
  once shares exist; relations between copied projects are connected. Comments,
  attachments, views, buckets and positions use native copying; there is no
  custom deep-copy engine. A `clone.pending` entry marks an uncertain duplicate
  POST: verify in the provider, record the new ID under `clone.projects`, and
  clear it only once verified; never infer a copy from a similar title or retry
  the POST automatically. Do not rerun clone after normalization.
- **Staging writes** are restricted to staging tasks, relations and endpoints.
  Moving staging tasks changes visible numbers and would break index pairing,
  so the first move saves `clone.tasks`, the source-to-staging mapping, and
  `clone --apply` refuses afterwards. Deleting an emptied staging subproject
  records the source in `clone.removed`; a removed copy that still exists
  blocks cutover until the delete is rerun.
- **Checks.** Attachment and comment counts, assignments and internal source
  relations are verified before normalization and again before cutover. Added
  journal comments are allowed. Labels are global: adoption may create missing
  `ab:tier:*` labels and edit staging attachments, never rename or delete global
  labels. Link hashes, IDs and task UIDs change; history, webhooks, reactions and
  subscriptions are not migrated.
- **External relations** are best effort. Clone and cutover add missing
  `related`, `duplicateof`/`duplicates`, `precedes`/`follows` and incoming
  `blocked` relations from staging; Vikunja adds the inverse, which needs read
  access to the external task. Outgoing `blocking`, external parent/subtask,
  `copiedfrom`/`copiedto` and unknown kinds are skipped for a human decision and
  reported as `manual`. Skipped edges are warnings with a short fixed staging
  comment; a failure to post it is `comment_warning` for that apply only.
  Comments never determine resolution.
- **Cutover** checks the copy and audit, prepares the managed repository
  instructions, renames the original to `TITLE — backup ID` and staging to
  `TITLE`, then atomically writes the new recursive binding. Before switching it
  retries eligible external edges and rechecks the audit; lost write responses
  are checked against live tasks. Actual names and the binding decide what
  remains on a rerun. Nothing is deleted and no restoration is attempted.
- Plan sync runs only after cutover, because it reads the current binding, not
  the receipt.

## GitHub Projects

- **Repository from origin.** The binding names a project; the repository is
  origin's, read from Git, because the binding file lives in that repository and
  a stored copy could only disagree with it.
- **State.** A closed issue is Done whatever its column, because GitHub keeps
  issue state and card apart: reopening leaves the card in Done, and with the
  Item closed workflow off a closed issue may sit anywhere. An open issue in Done
  reads as `Unknown`.
- **Writing Done.** The card moves first, then the issue closes. A failure
  between the two leaves an open issue in Done, which reads as `Unknown` and is
  finished by any rerun; the other order would leave a closed issue in an old
  column reading as Done, which nothing revisits. Closing as not planned also
  corrects an issue the board's auto-close already closed as completed. Leaving
  Done reopens the issue. Board workflows can land a few seconds after a write
  and overwrite it, so writes are reread with short pauses and a transition a
  late workflow overwrote is written once more.
- **Duplicates** are a closing reason, so marking one closes the task as Done
  and moves its card; removing the mark leaves it closed.
- Fields and options are read once per process and never persisted: an option
  ID kept in the repository would outlive the option.

## Jira

The adapter uses REST v2 text fields on both deployments; Cloud's enhanced
`/search/jql` uses cursor pagination, while Server/DC's `/search` uses offsets.
Cloud search retrieves keys and hydrates issues through the v2 issue endpoint:
enhanced search can return ADF even under v2, which must not be flattened into
checklist text.
Deployment type is read from `serverInfo`; user identities use Cloud account IDs
or Server/DC usernames accordingly. The optional connection `username` selects
email/API-token Basic authentication; its absence retains PAT Bearer auth.
This additive optional account field requires no format migration: old
URL/token accounts retain their serialized shape and published fixtures.

Lifecycle uses project workflow statuses from `/project/KEY/statuses`, checked
for every issue type. Writes follow available transitions, never assume that
a status ID is a transition ID. Parentage uses native subtasks; dependency
links use the direction of the native outward description. Comments contribute
to checklist revisions even when Jira leaves the issue timestamp unchanged.

Existing MCP solutions were evaluated: Atlassian's official server targets
Cloud, and `sooperset/mcp-atlassian` supports Cloud and Server/DC. Neither
replaces the portable lifecycle, scope, revision or uncertain-write contract.
Direct REST avoids an additional server process, MCP client transport and
third-party runtime dependencies for the same adapter logic. Direct MCP access
for agents can be considered separately from tracker workflow support.

## Live checks

The offline suite never touches a real tracker. Two opt-in scripts create and
remove their own test data and never accept an existing project as a target:

```bash
PYTHONPATH=. python3 tests/live_vikunja_adoption.py --run
PYTHONPATH=. python3 tests/live_github_tracker.py --run --project OWNER/N --repository OWNER/REPO
```

## Container access

An enabled tracker renders connections and policy into an immutable snapshot
under `runtime/tracker/workspaces/<id>/sessions/<session>/config.json`
(directory 0700, file 0600). A box receives only its workspace's snapshot
directory, read-only; sessions in that box share it. Workflow evidence, locks,
counters and import checkpoints have their own read-write state mount. Secrets
never enter Podman argv.
