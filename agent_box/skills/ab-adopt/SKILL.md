# ab-adopt

Before coordinating work, read `agent-box workflow behavior --role coordinator`; follow its effective instructions and startup guidance notice. Assigned delegates use the behavior in their assignment.

GitHub Projects has no staging copy: bind it with ab-setup, run its board init, then ab-normalize the existing issues in place. The steps below are Vikunja's.

1. Resolve the source by exact project ID or full path. For the board proposal, start with `agent-box tracker provider vikunja board init ID --recursive` and the metadata-only procedure linked below; do not read cards to infer column meanings. A later adoption audit and task normalization may read task text, comments and relations for their own purpose. Explain findings in the user's language. Agree on a quiet editing window: neither source nor staging should change concurrently. Use ab-tracker for reads and `search QUERY --include-done` when inspecting history or relations. Adoption preserves meaning; never implement, investigate implementation, design solutions, merge tasks, or create subtasks because work looks large.
2. Preview `tracker adopt clone --project ID`, then add `--apply` within the authorized scope. The provider clones the whole tree; existing source IDs, data and integrations remain available. The receipt defaults to `<workflow state>/adoptions/<repository key>/<source ID>.json`, which is shared with the host and survives box recreation; `boards` and `cutover` find it when it is the repository's only receipt, otherwise pass `--receipt PATH`. Inside a box an explicit receipt must stay under workflow state. Tell the user the reported `receipt` path (PATH below) and both root IDs. Shares use native copying; labels remain shared, and new link shares have new URLs. Inspect the provider's reported limitations, external relations, filters and embedded links. Do not involve the structured importer.
3. Normalize only through `tracker --adoption PATH ...`. This selects staging without saving a binding and refuses writes to source or external tasks. Prepare each staging board using the shared [board preparation](../ab-setup/board-preparation.md) procedure and `tracker adopt boards --receipt PATH`; mappings and saved plans use `--project STAGING_ID`. Propose meanings from metadata, obtain confirmation of the concrete plan, then apply that file. Source IDs cannot be reused as staging IDs. Read `tracker --adoption PATH audit` after preparation. Never bind staging early or run implementation workflows against it. Do not run ab-sync in staging: it targets the current repository binding; reconciliation belongs after cutover.
4. Work one project at a time, normalizing each task exactly as ab-normalize describes, with `--adoption PATH` on every command. Adoption adds only this: remove any inherited marker first with `tracker --adoption PATH normalized ID --undo`; show proposed title/description rewrites before applying unless already approved; never inspect repository implementation to manufacture acceptance or completion. New implementation plans or decomposition belong to ab-plan; evidenced relation repair is part of adoption.
5. Every `update`, `tier`, `state`, `relation`, `comment` and checklist command takes `--adoption PATH`. Relations are analyzed across the complete selected tree, not only the task in hand. Preserve valid explicit tiers and resolve malformed or conflicting tier labels from evidence; assign new ones only by ab-plan's tier rule, and creating missing global `ab:tier:*` labels is allowed. Staging may map an existing In progress status without claiming work, but may not mark unfinished work Done. Collapsing subprojects is optional: only at the user's request, `tracker --adoption PATH move TASK... --project P` moves staging tasks between staging projects, and `tracker --adoption PATH delete-project P` then deletes an emptied staging subproject; the receipt saves the task mapping and each removal first, so cutover still verifies the copy. Never rename or delete global labels, including `ab:` labels; change only staging task attachments. Fixed diagnostic comments generated automatically by agent-box may be English; do not rewrite or translate them merely for localization.
6. Re-run the staging audit; ab-normalize says when a task is marked and what the marker means. Structural errors and unexplained missing internal relations prevent cutover. Use staging `relation ... --remove` for intentional corrections: the receipt records that exact removal before the API call, and adding the relation back clears it. Retry interrupted edits from live state; never edit the receipt to waive unexplained losses. External relation omissions are warnings. Clone and cutover try external `related`, duplicate, ordering and incoming blocker relations from staging; Vikunja also adds the inverse on the external task. External parent/subtask, outgoing blockers, copy provenance and unknown kinds need human decisions: absent edges are skipped; existing edges stay `manual` with the policy warning. Journal options for unsafe types require agreement on structure, external workflow or provenance, not simply manual addition. External or unreadable children are structural audit errors even when only the parent is in scope. Comment failures appear as `comment_warning` only in the current apply report; read-only reports do not verify journal delivery or recover earlier posting failures. Explain these warnings in the user's language. A missing `related` alone does not reset historical status. Never remove source relations or expand external editing to make adoption pass; reports read live relations.
7. Preview `tracker adopt cutover`, then `--apply` when the reviewed result is authorized. It prepares managed repository instructions, renames source to its explicit backup name, renames staging to the original name, and writes the new binding last. Report both IDs, the binding, and unresolved Backlog work. Original task links and integrations still address the backup; migrate integrations separately.
8. To continue after interruption, audit staging or rerun cutover against the same receipt; actual names and binding determine what remains. Cutover retries missing eligible external relations before renaming, without rerunning clone normalization. Once binding is switched, repeated cutover only reads the current report. Resume `clone` only before normalization. A pending duplicate means the POST result is uncertain: inspect the provider, record the verified new project ID in the receipt's `clone.projects`, and clear `clone.pending` only after verification. Never blindly repeat that POST. Do not infer copies from similar titles, delete incomplete staging automatically, or restore tracker state. Destructive integration tests use only purpose-created test projects.
