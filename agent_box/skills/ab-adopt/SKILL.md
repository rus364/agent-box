# ab-adopt

1. Resolve the source by exact project ID or full path. Read `agent-box tracker audit --project ID --recursive`, existing task text, comments and relations. Explain the notes in the user's language. Agree on a quiet editing window: neither source nor staging should change concurrently. Adoption preserves meaning; never implement, investigate implementation, design solutions, merge tasks, or create subtasks because work looks large.
2. Preview `tracker adopt clone --project ID --receipt PATH`, then add `--apply` within the authorized scope. The provider clones the whole tree; existing source IDs, data and integrations remain available. Keep the receipt outside repository control files and tell the user its path and both root IDs. Shares use native copying; labels remain shared, and new link shares have new URLs. Inspect the provider's reported limitations, external relations, filters and embedded links. Do not involve the structured importer.
3. Normalize only through `tracker --adoption PATH ...`. This selects staging without saving a binding and refuses writes to source or external tasks. Preview `tracker adopt boards --receipt PATH`, then `--apply`; ambiguous boards need an explicit decision. Read `tracker --adoption PATH audit` after repair. Never bind staging early or run implementation workflows against it.
4. Work one project at a time. Show proposed title/description rewrites before applying unless already approved. Preserve the task's language, scope, unrelated text and import markers. Make Goal, Context, Acceptance and Validation explicit only from existing evidence. Extract a checklist only where justified. Missing human decisions remain explicitly unresolved in Backlog for later ab-interview. New implementation plans, dependencies or decomposition belong to ab-plan, not adoption. Do not inspect repository implementation to manufacture acceptance or completion.
5. Use existing `update`, `tier`, `state`, `relation`, `comment` and checklist commands with `--adoption PATH`. Assign tiers 1-3 when supported by the material; creating missing global `ab:tier:*` labels is allowed. Unresolved estimates remain Backlog warnings. Preserve assignments, historical progress and meaningful relations. Staging may map an existing Doing status without claiming work, but may not mark unfinished work Done. Never rename/delete global labels, including ab: labels; change only staging task attachments. Explain substantial changes in short task-language comments, with no machine-readable bookkeeping.
6. Re-run the staging audit. Structural errors and missing internal relations prevent cutover; external relation omissions are warnings. Clone and cutover try external `related`, duplicate, ordering and incoming blocker relations from staging; Vikunja also adds the inverse on the external task. External parent/subtask, outgoing blockers, copy provenance and unknown kinds need human decisions: absent edges are skipped; existing edges stay `manual` with the policy warning. Journal options for unsafe types require agreement on structure, external workflow or provenance, not simply manual addition. External or unreadable children are structural audit errors even when only the parent is in scope. Comment failures appear as `comment_warning` only in the current apply report; read-only reports do not verify journal delivery or recover earlier posting failures. Explain these warnings in the user's language. Keep work requiring clarification in Backlog; a missing `related` alone does not reset historical status. Never remove source relations or expand external editing to make adoption pass. Comments are human journal, never resolution flags; reports read live relations.
7. Preview `tracker adopt cutover --receipt PATH`, then `--apply` when the reviewed result is authorized. It prepares managed repository instructions, renames source to its explicit backup name, renames staging to the original name, and writes the new binding last. Report both IDs, the binding, and unresolved Backlog work. Original task links and integrations still address the backup; migrate integrations separately.
8. To continue after interruption, audit staging or rerun cutover against the same receipt; actual names and binding determine what remains. Cutover retries missing eligible external relations before renaming, without rerunning clone normalization. Once binding is switched, repeated cutover only reads the current report. Resume `clone` only before normalization. A pending duplicate means the POST result is uncertain: inspect the provider, record the verified new project ID in the receipt's `clone.projects`, and clear `clone.pending` only after verification. Never blindly repeat that POST. Do not infer copies from similar titles, delete incomplete staging automatically, or restore tracker state. Destructive integration tests use only purpose-created test projects.
