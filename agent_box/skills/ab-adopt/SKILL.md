---
name: ab-adopt
description: Bring an existing tracker project and its subprojects in line with the agent-box workflow without implementing anything.
---

# ab-adopt

1. Resolve the project exactly first: a numeric ID or a full project path from `tracker projects`, never a guess from a partial title. A project with subprojects is adopted with the whole subtree, so every later command carries `--recursive` and covers every project under the root.
2. Read `agent-box tracker audit --project ID [--recursive]`. Before a binding exists it reports the `notes` and the board problems; after step 5, plain `tracker audit` adds per-task problem codes and their counts. Explain the notes to the user in their own language rather than repeating the English text. Adoption only rewrites tracker data. Never implement, design or start work described by any task.
3. Take the snapshot before the first write of any kind: `tracker provider vikunja snapshot --project ID --recursive --out PATH`. It holds the projects, tasks, comments, labels and every board's views and buckets, plus the moment it was taken, which is the whole tracker side of adoption; the repository files step 5 writes are Git's to revert. It also records which tracker it came from, and restore refuses a snapshot taken from another one. Tell the user where the file is and that `tracker provider vikunja restore PATH` compares against it and, with `--apply`, puts the tracker back.
4. Repair boards: `tracker provider vikunja board init PROJECT [--recursive]`, inspect the dry run, then `--apply`. It only adds missing lifecycle columns and sets the view's done column. The whole subtree is planned before anything is written, so a board that is ambiguous, filter-built or has no single kanban view is reported as blocked and left for the user; a failure during the writes still leaves earlier projects repaired, and re-running is safe because the repair is idempotent.
5. Bind with `tracker setup --project ID [--recursive] --apply`. This writes repository files, not tracker data. Then run `tracker audit` and interview the user for what the audit cannot know: the language tasks are written in, what their existing labels and columns have historically meant, which tasks to leave alone, and whether stalled Doing tasks are abandoned. Ask one material question at a time with concrete options.
6. Work in batches, one project at a time. Apply mechanical fixes directly: lifecycle column, `tier 1-3` for every implementation task, real `relation` edges, removed contradictions. Show proposed title and description rewrites before applying them. A rewrite makes Goal, Context, Acceptance and Validation explicit in the task's own language and preserves the original meaning; it never decides the work differently, and it never drops an import marker such as `Vikunja external ID:` that the description already carries.
7. Labels the project already uses are the user's; only `ab:` labels are yours. Leave one short comment per changed task, in the task's language, saying what was wrong, what changed and on what evidence. Comments stay a human journal: nothing machine-readable, and no adoption bookkeeping.
8. Use read-only scouts (`workflow prepare TASK --role scout --tier 0`) only for questions that need the repository read - does this task already exist in code, do these two tasks duplicate each other. They need the binding in place, so they are available only after step 5, and they are optional: this whole skill runs in whatever session the user started, with whatever model they chose.
9. Re-run `tracker audit` as acceptance. Whatever it still reports is what is left, so an interrupted adoption resumes by auditing again. Report the remaining problems and the snapshot path to the user. To roll back, `restore` makes the tracker the state the snapshot recorded, rather than merging it with what happened since. Task text, labels, assignees, relations, columns, project titles and parents go back; a task moved away returns to its project, keeping its ID; and everything created since inside the snapshot's projects is deleted - tasks, columns, comments whoever wrote them, and agent-box's own `ab:` labels. Labels outside that namespace are global and may serve another project, so they are only reported. What cannot be made true again is a blocker: a task, project or comment deleted since cannot be recreated with its own ID, author and time, and an object older than the snapshot that the snapshot does not list was moved in from somewhere it cannot describe. `restore --apply` writes nothing while blockers stand; `--allow-partial` restores everything else and leaves them reported.
