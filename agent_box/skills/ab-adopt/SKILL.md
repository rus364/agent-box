description: Bring an existing tracker project and its subprojects in line with the agent-box workflow without implementing anything.
---

# ab-adopt

1. Read `agent-box tracker audit --project ID [--recursive]`. Before a binding exists it reports the `notes` and the board problems; once the repository is bound, plain `tracker audit` adds per-task problem codes and their counts. Explain the notes to the user in their own language rather than repeating the English text; they state what adoption changes, what it never touches, and why a snapshot comes first. Adoption only rewrites tracker data. Never implement, design or start work described by any task.
2. Resolve the project exactly: a numeric ID or a full project path from `tracker projects`, never a guess from a partial title. A project with subprojects is adopted with the whole subtree, so `tracker setup --project ID --recursive` and everything after it covers every project under the root.
3. Take the snapshot before the first write of any kind: `tracker provider vikunja snapshot --project ID --recursive --out PATH`. It holds the projects, the tasks and every board's views and buckets, which is everything adoption changes. Tell the user where the file is; it is the only way back.
4. Then repair boards: `tracker provider vikunja board init PROJECT [--recursive]`, inspect the dry run, then `--apply`. It only adds missing lifecycle columns and sets the view's done column. The whole subtree is planned before anything is written, and a board that is ambiguous, filter-built or has no single kanban view is reported as blocked and left for the user to resolve.
5. Bind with `tracker setup --project ID [--recursive] --apply`, then audit. Interview the user for what the audit cannot know: the language tasks are written in, what their existing labels and columns have historically meant, which tasks to leave alone, and whether stalled Doing tasks are abandoned. Ask one material question at a time with concrete options.
6. Work in batches, one project at a time. Apply mechanical fixes directly: lifecycle column, `tier 1-3` for every implementation task, real `relation` edges, removed contradictions. Show proposed title and description rewrites before applying them. A rewrite makes Goal, Context, Acceptance and Validation explicit in the task's own language and preserves the original meaning; it never decides the work differently, and it never drops an import marker such as `Vikunja external ID:` that the description already carries.
7. Labels the project already uses are the user's; only `ab:` labels are yours. Leave one short comment per changed task, in the task's language, saying what was wrong, what changed and on what evidence. Comments stay a human journal: nothing machine-readable, and no adoption bookkeeping.
8. Use read-only scouts (`workflow prepare TASK --role scout --tier 0`) only for questions that need the repository read - does this task already exist in code, do these two tasks duplicate each other. They need the binding in place, so they are available only after step 5, and they are optional: this whole skill runs in whatever session the user started, with whatever model they chose.
9. Re-run `tracker audit` as acceptance. Whatever it still reports is what is left, so an interrupted adoption resumes by auditing again. Report the remaining problems and the snapshot path to the user.
