# Vikunja board preparation

Use this procedure from ab-setup and, for staging only, ab-adopt. Do not create a copy just to prepare a board.

1. Read metadata only: `agent-box tracker provider vikunja board init PROJECT [--recursive]`. During adoption use `agent-box tracker adopt boards --receipt PATH` instead; it inspects staging. Output includes view/default/done IDs, column IDs, names, positions, available counts and lifecycle diagnostics. Do not read task text, comments, `board show` or a full audit to guess column meanings.
2. Propose a mapping to Backlog, Ready, In progress, In review, Done from this metadata. Reuse suitable existing columns; mark uncertain meanings as assumptions for the user to correct. No alias dictionary is authoritative. Missing confidence does not authorize more research. Keep existing canonical columns instead of creating duplicates. Unknown columns remain; moving cards, merging or deleting columns needs a separate concrete proposal and approval.
3. Write a temporary mapping JSON outside the repository: exactly the five state names, each valued by an existing bucket ID or `null` to create. Build one plan at a time: `agent-box tracker provider vikunja board init PROJECT --mapping MAPPING > PLAN`. In adoption replace the command prefix with `agent-box tracker adopt boards --receipt PATH --project STAGING_ID --mapping MAPPING > PLAN`; specify the exact staging project even in a recursive tree. Never bind staging or use the provider route to bypass adoption boundaries.
4. Present the concrete plan in the user's language: project/view, each old name and ID → target state, create/rename/reuse actions, final order, retained columns and default/done changes. Lifecycle columns come first in canonical order; retained columns follow in their prior relative order. Explain assumptions and ask the user to confirm or correct this plan before any write. A request to set up/adopt is not confirmation of an unseen plan. Corrections require regenerating and showing the plan.
5. Only if the user separately requests investigation of column meanings, use the configured inexpensive scout and a bounded sample from disputed columns. Use the supported workflow scout route of an existing bound task, following ab-plan; give it the disputed columns and a small explicit sample budget, and request concise recommendations with uncertainty. Its read is `agent-box tracker provider vikunja board sample PROJECT --bucket ID --limit 3`; staging uses `agent-box tracker adopt boards --receipt PATH --project STAGING_ID --sample ID --limit 3`. Each reads one page, no comments or expansions. Do not load the board into the coordinator, start research merely because a guess is uncertain, manufacture a task or bind staging to obtain a route. If no supported scout route is available, report that and ask the user to clarify the meaning; do not silently choose another model or broader read. Return to step 4 with the recommendations.
6. Preview the saved plan with the same command prefix and `--plan PLAN`. After the user's confirmation, add `--apply`, keeping the exact file. The command checks server/project/view and the observed board before writing. A conflict or unknown write outcome requires fresh metadata and a newly reviewed plan, never blind retries. A fully applied plan reports already-applied. Plans are temporary operation input, not a persisted lifecycle mapping; never save their IDs in `.agent-box.json`.

Afterward reread metadata and continue setup or staging normalization. Preparing a board does not rewrite task descriptions or reconcile existing task done flags when the done bucket is changed.
