# ab-land

An accepted task lands by its configured route without asking: merge it, and open its pull request where the route calls for one. Ask the user only about a blocker or disputed scope. Unattended runs return needs-human. Never bypass branch protection or force-push.

1. Read the parent task and `workflow inspect PARENT` on its branch for the effective configuration source, merge mode, scope and review triggers; never choose the route from host/default config inside a container. Then use `workflow land PARENT inspect`. In GitHub mode it finds the PR by parent branch and base; several matches stop instead of guessing. Confirm PR identity and head, inspect CI, unresolved threads and comments. In local mode it reports the exact local task/base refs, ancestry and completion blockers; GitHub is not contacted. Use read-only scouts only when useful. No parallel implementation.
2. Review follows one policy in both modes; the `workflow inspect` of step 1 names the route under `review.route`. Run every round by ab-review, which covers the cloud route in the parent pull request as well as local ones.
3. Verify feedback against code and requirements by ab-review's evidence and proportionality rules. Push back with evidence; escalate material disagreement/out-of-scope requests without self-awarding PASS, updating affected tasks/dependencies. Resume the assigned In review task with `tracker claim PARENT --resume`. Fix valid findings sequentially with a bounded worker or primary for tiny changes; prefer local fixes/reuse, justify redesign and preserve required checks. Keep progress in the working language (ab-tracker). Reviewers stay read-only; primary handles gh comments/thread resolution after verifying fixes, writing replies in the `configuration.language` that `workflow inspect` reports when one is set.
4. Fix while In progress, directly or with a fresh worker, then return to In review after acceptance. Commit fixes, run the project's validation with `workflow validate PARENT -- COMMAND ARGS`, then review the current head by the reported route: the policy decides whether a verdict is needed, `off` and a non-triggering `auto` need none in either mode, and SKIPPED is never a PASS. A current-head APPROVED review by a person is acceptance; an app's approval, and any bot reaction, is not. Either mode permits the user's explicit acceptance of the current head with `workflow approve PARENT --reason TEXT`; an instruction to avoid delegation is not one. Push the parent safely only in GitHub mode.
5. Inspect the enforced review budget used/limit/remaining and failures, and stop on repeated findings without progress. One budget covers both routes: a verdict read from the pull request spends an attempt exactly like a local one, and a published request that nobody answered spends none. Follow ab-review for failures and a user's additional allowance. Keep a short iteration summary in the tracker. CI failure, stale review, unaddressed threads, uncertainty or timeout prevents merge.
6. Merge by the configured route. In GitHub mode `workflow land PARENT merge [--method squash|merge|rebase]` pins the expected head and defaults to squash; a queued merge is not Done, and the merged PR must retain the exact head/base and merge identity. In local mode `workflow land PARENT merge` takes no method: it fast-forwards the local default base to the exact accepted head and, with auto_push enabled (the default within opt-in workflow), publishes only that head to the unique effective origin with Git credentials alone, no GitHub API and no task-branch publication. One command is the whole landing: acceptance of the head, merge, publication, Done, cleanup. After any failure run the same command again; it continues from the step that failed, never merges twice, and publishes nothing but the accepted head. Never force-repair a remote; explicit auto_push=false completes locally.
   A refusal names what is missing. Every acceptance and validation item of the parent and its subtasks must be closed by now, including a manual check that no earlier step required. Without acceptance for this exact head, including after a new clone, switch to the task branch, run `workflow validate PARENT -- COMMAND ARGS` and the reported review route as required, or record the user's decision with `workflow approve PARENT --reason TEXT`, then merge again. When the base already contained the accepted head, its empty diff proves no work: review the complete implementation from requirements, code and Git history, or take explicit acceptance; an empty diff is never a PASS and unclear scope is INCONCLUSIVE. Diverged branches, a moved head, an unknown or diverged remote and a changed default branch all stop the merge: inspect Git instead of resetting the base or marking Done by hand.
7. Handle the merge result’s Plan sync outcome through ab-sync before starting dependent work. Report `cleanup` outcomes separately from merge and Done. `workflow.cleanup_local_branches` and `workflow.cleanup_remote_branches` are independent and off by default, and run only after a successful completion, over the parent and the completed subtasks of the live tracker hierarchy. A ref is deleted only where the base contains its head; in GitHub mode the merged PR head is that proof, exactly for the parent and by ancestry for its subtasks, and local mode also requires the head in the live published origin base. A remote copy is deleted only where it exists. Unfinished subtasks, the current branch, worktrees, base, symbolic, ambiguous and moved refs survive with their reason, as do hierarchy errors. `workflow finish` already releases a finished subtask's own branch under the same settings. For a Done parent `workflow land PARENT cleanup` retries the configured policy without merging or writing the tracker, and missing refs are no-ops. Cleanup never publishes the base or force-repairs a branch. Do not enable cleanup settings merely to finish landing.
