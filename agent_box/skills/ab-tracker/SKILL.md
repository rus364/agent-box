# ab-tracker

Use `agent-box tracker --help` and command help for exact arguments. Output is JSON by default; no `--json` flag. Never call a provider API directly for common operations.

- `agent-box tracker status` reads account, binding and lifecycle. User references follow `tracker resolve REFERENCE` rules (quote `#21`); use `resolve` itself only to narrow: `--title` forces title matching, `--project PROJECT` limits to one bound project. A unique exact match selects automatically; ambiguity requires the user to choose among the reported projects/tasks. No match means ask for a title/project/URL; never substitute full-text search results.
- `tracker get REFERENCE` reads requirements and comments; it takes a visible number, exact title, URL or canonical ID, so no separate resolve is needed. A bare number that is one task's ID and another's visible number is refused; pass the quoted `#N` or the URL. Pass the returned canonical `id` unchanged to mutations and workflow. Before writing, compare number, project and title with user intent. `search`, `ready`, and `next` return compact summaries; text search finds candidates, not exact references. URLs identify their own tasks without adoption redirects.
- `search --exclude-label ab:normalized` omits processed tasks before output; unfiltered compact search still finds relation candidates. `normalized ID...` marks completed normalization for one or more tasks and `normalized --done [--project P] [--recursive]` marks every completed task in scope at once; `--undo` removes only that marker for reprocessing. Neither command changes lifecycle.
- `claim ID` checks readiness and ownership, assigns the API-key user and enters Doing. `--resume` is deliberate same-user recovery. Assignment is a cooperative lock, not distributed exclusion. Recheck ownership before writing.
- `create`, `update`, `tier`, `relation`, `comment`, and `check` maintain tasks. `checklist ID` prints the task's revision with the item indices; `check ID INDEX... --revision REVISION` records every named item in one write and refuses a revision the task has already moved past; `--undo` retracts contradicted evidence. Read `checklist` immediately before `check`: the revision belongs to the whole task, so a journal comment moves it too. Files/stdin carry multiline text.
- `state TASK... STATE` moves one or more tasks; `Doing` belongs to `claim`, and `Done` belongs to `workflow finish`, which proves integration. `state TASK... Done --reason TEXT` closes tasks that were never implemented and journals that reason on each; it refuses while a task's `ab/<id>-` branch still holds commits neither the base nor the parent branch contains, and checks every named task before moving any of them.
- Infer relations from task evidence: a blocker must be necessary for completion, not merely share a topic; use `related` for a meaningful nonblocking connection. Add or correct evidenced links, including existing ones; ask about material uncertainty, preserve unrelated links, and journal substantial changes.
- Create a new task in the user's interaction language; use the task's language for descriptions, comments and normalization. Preserve unrelated text. First-class fields hold status, priority, assignee, relations and tier; do not duplicate them in Markdown.
- Assess priority when creating or preparing tasks: use explicit urgency, deadlines and consequences of delay. Set or revise existing values when evidenced; ask about material uncertainty, and never infer urgency from an unset value. Use `create --priority N` or `update ID --priority N`: 0 unset, 1 low, 2 medium, 3 high, 4 urgent, 5 immediate. During incremental normalization assess only selected candidates, not the marked backlog. Preserve existing values without evidence for a change; priority is separate from dependencies, lifecycle and tier. Journal substantial changes briefly.
- Descriptions follow ab-plan's section format. Checkboxes record evidenced progress, not reviewer acceptance. Decisions and failures belong in short comments.
- Comments are a human journal only. Branch, base branch and pull request are read from Git and GitHub; no comment can set them, and nothing machine-readable belongs in one.
- The coordinator reads and writes tracker state and alone owns requirements, lifecycle, dependencies, progress comments, checkboxes, branches and GitHub. Delegated workers, reviewers and scouts use their supplied self-contained assignment and repository instructions, without rereading tracker comments or history, and report back. This contract is the same for native subagents and agent-box-managed CLI runs; it is not credential isolation.
- Required states: Backlog, Ready, Doing, Review, Done. Dependencies block deterministically; a completed sibling unblocks after parent-branch integration, while an external parent's work must first merge into base.
- `audit --project ID --recursive` reads the complete project tree without saving a binding. Structural errors block adoption; warnings about Backlog preparation, historical progress and duplicate titles stay visible without forcing invented requirements.
- `adopt clone|boards|cutover --receipt PATH` orchestrates native staging adoption. Use `--adoption PATH` before ordinary tracker subcommands to normalize only staging tasks. Source data stays intact until the final root rename; the binding switches last.
- Use `agent-box workflow finish ID` for completion. Provider-specific imports, boards, bulk edits and product fields are under `tracker provider vikunja --help`; inspect dry runs before applying. After adoption, imports with preserved external IDs must select `--project NEW_ROOT_ID` so the backup's markers and checkpoints cannot redirect updates. Unsupported providers fail explicitly.
