# ab-review

Before coordinating work, read `agent-box workflow behavior --role coordinator`; follow its effective instructions and startup guidance notice. Assigned delegates use the behavior in their assignment.

1. Before a round, read `tracker checklist ID` and confirm ab-work's acceptance-to-evidence check is complete, including child integration for a parent; checkmarks alone are not evidence. An item only the user can close, such as a check that cannot run from here, never holds up the round; landing is where every item must be closed. The reviewer receives the complete descriptions of the task and its parent (for a parent, every subtask's) but no comments, so move decisions from discussion into the description first. The reviewer reads referenced repository sections and checks code against them; it never synchronizes live tasks. The reviewer judges only what the repository shows; items about tracker state or operator actions are yours to close with evidence in the checklist, and the reviewer lists them under limitations rather than returning INCONCLUSIVE for them. Read `workflow inspect ID` for policy, triggers, budget and any pending round.
2. For each new round, choose anew from current `workflow inspect ID` `execution.reviewer`; `authors-required` means rerun inspect with `--author VENDOR...` naming every vendor that wrote the reviewed code (`codex`, `claude`, or the external API name of a `PROVIDER@API` model, including yourself and every worker), or `--author unknown` when you cannot tell, and run its `managed` command as given: `cloud` follows step 10; `delegate` uses the named `native` profile when it matches your session provider and API identity and is available with the configured model, effort and speed, otherwise its `managed` command. `effort=default` and explicit `speed=standard|fast` stay managed because native agents cannot pin those requests. A thread-limit error from another assignment or earlier round does not establish current unavailability. Never skip the first candidate for a later native profile. `native` (empty reviewer list) requires a fresh independent native reviewer, never self-review. Native uses step 3. Managed: `workflow review ID [--brief FILE]` applies off/auto/always (SKIPPED is not PASS) and, with `workflow.review.incremental`, judges commits after an applied round by their delta (an `outcome` accepted by the delta threshold opens no round and is not PASS) and runs the first available candidate of the reviewer list; the next candidate runs only after unavailability, authentication, quota or timeout. `--brief` is an optional compact English note outside the working tree on what the tracker lacks, such as risks and validation limits.
3. Native: `workflow review ID --native [--brief FILE]` opens the round and prints `message` pointing to complete file pages. If policy or incremental evaluation returns an outcome without `message`, no round opened; do not spawn. Otherwise attempt a fresh read-only reviewer spawn, using the selected profile when configured, without the parent's history (`fork_context=false` in Codex), and pass `message` as its whole prompt; never resume or reuse an earlier reviewer. Save its final message unchanged to a file outside the working tree, then `workflow review ID --result FILE --provider PROVIDER --model MODEL [--effort EFFORT]` naming what actually ran. If this spawn fails and reviewer candidates are configured, briefly tell the user the current reason and use step 2's managed command within step 5's failure budget. Do not loop spawn or change candidates solely because of a thread limit. Without configured reviewer candidates only native works.
4. The reviewer answers in Markdown with exactly one line `Verdict: PASS|NEEDS_WORK|INCONCLUSIVE` and findings `- [LOW|MEDIUM|HIGH|CRITICAL] path:line — text`. No verdict line, several, or a PASS with findings is a failure; fix nothing in the answer yourself.
5. Budget: `max_rounds` counts received verdicts only. A failure (killed process, provider error, a native reviewer that never answered, no verdict line) spends no attempt and may be rerun; a native answer without a verdict line ends its round, so rerun with `--native`. After 2 failures in a row, or when the budget is exhausted, review stops: ask the user. Only on their explicit decision run `workflow review-budget ID --reason TEXT [--limit TOTAL]`, where TOTAL = used + extra rounds; it also clears the failure streak. Never raise it yourself or put budget history in a brief.
6. Right after every round result (managed, native or GitHub cloud) and before any fix or next step, send the user a compact status block in their language: a bold header `Review #N, round X/Y — VERDICT` with the reviewer model; one bullet per finding with severity, location, essence and your assessment (agree, or dispute with a short reason); then a bold `Next:` line with the next step. PASS has no bullets.
7. Then read `reconciliation.status`. `applied` recorded acceptance. `stale` (a new commit or moved base), `superseded` (a newer round) and `invalid_input` accept nothing. For `saved`, `error` or `blocked`, restore the condition (task branch, clean tree, tracker access) and run `workflow review-result ID --round=ROUND --reconcile`: no new reviewer call or attempt; a missing oversized-report summary may use the configured scout once. `review-result` names `result_path` (the full answer) and `stream_path` (raw provider streams, kept until the task is Done). When `report_text` is present, read its generated pages through the final marker for the delivered report or labelled scout summary; keep `result_path` as original provenance and verify consequential claims against it. Read streams only to diagnose INCONCLUSIVE, a failure or a disputed result. Never copy private answers or streams into the tracker or public output, edit workflow state or restore refs to revive acceptance.
8. Verify each finding against code and requirements. Reject taste-only, quota-driven or hypothetical blockers; a complexity finding needs a location, a real cost and a simpler behavior-preserving alternative. Journal valid findings in the tracker language (ab-tracker), uncheck only contradicted items, resume with `tracker claim ID --resume`, then fix, commit, validate and review sequentially within budget. Push back with evidence, escalate material disagreement or no progress, and never self-award PASS.
9. For already-integrated parent recovery the round asks for review of the complete implementation from requirements, code and Git history; an empty diff is not acceptance whatever the policy says, and unclear scope is INCONCLUSIVE. `workflow approve ID --reason TEXT` records the user's explicit acceptance of the current head, never a verdict.
10. Cloud: in GitHub mode with `github_provider` codex or claude, `workflow inspect ID` reports `review.route` as that bot in the parent pull request. There `workflow review PARENT` publishes one request per head and every rerun reads the answer back into the same budget, receipts and status; it never asks twice, needs the pull request to carry this exact head (ab-pr first), and refuses a model or effort the bot cannot pin. No answer yet is not a verdict: rerun later, and after `wait_seconds` the round ends as a failure that spends no attempt — report it and ask the user instead of reviewing locally on your own. Subtasks keep local rounds.

Never paste a diff into any role assignment. Review assignments carry exact requirements/instructions, commit boundaries, a compact change summary and evidence references. The complete path inventory and diff stay separate, hash-bound evidence; the reviewer inspects bounded path/source/diff ranges as needed, with renamed files still in scope. Oversized notes/reports use one labelled configured-scout summary; original verdict/finding identity stays authoritative. An unresolved input-size or summary failure opens no reviewer round: report it to the user without raising limits or splitting the assignment. Native final answers return directly.
