# ab-review

1. Before a round, read `tracker checklist ID` and confirm ab-work's acceptance-to-evidence check is complete, including child integration for a parent; checkmarks alone are not evidence. The reviewer receives the complete descriptions of the task and its parent (for a parent, every subtask's) but no comments, so move decisions from discussion into the description first. Read `workflow inspect ID` for policy, triggers, budget and any pending round.
2. Managed: `workflow review ID [--brief FILE]` applies off/auto/always (SKIPPED is not PASS) and runs the first available candidate of the reviewer list; the next candidate runs only after unavailability, authentication, quota or timeout. `--brief` is an optional compact English note outside the working tree on what the tracker lacks, such as risks and validation limits.
3. Native: `workflow review ID --native [--brief FILE]` opens the round and prints `message`. Start a brand-new read-only reviewer in fresh context without the parent's history and pass `message` as its whole prompt; never resume or reuse an earlier reviewer. Save its final message unchanged to a file outside the working tree, then `workflow review ID --result FILE --provider PROVIDER --model MODEL [--effort EFFORT]` naming what actually ran. Without configured reviewer candidates only native works.
4. The reviewer answers in Markdown with exactly one line `Verdict: PASS|NEEDS_WORK|INCONCLUSIVE` and findings `- [LOW|MEDIUM|HIGH|CRITICAL] path:line — text`. No verdict line or several is a failure; fix nothing in the answer yourself.
5. Budget: `max_rounds` counts received verdicts only. A failure (killed process, provider error, no answer, no verdict line) spends no attempt and may be rerun. After 2 failures in a row, or when the budget is exhausted, review stops: ask the user. Only on their explicit decision run `workflow review-budget ID --reason TEXT [--limit TOTAL]`, where TOTAL = used + extra rounds; it also clears the failure streak. Never raise it yourself or put budget history in a brief.
6. Right after every round result (managed, native or GitHub cloud) and before any fix or next step, send the user a compact status block in their language: a bold header `Review #N, round X/Y — VERDICT` with the reviewer model; one bullet per finding with severity, location, essence and your assessment (agree, or dispute with a short reason); then a bold `Next:` line with the next step. PASS has no bullets.
7. Then read `reconciliation.status`. `applied` recorded acceptance. `stale` (a new commit or moved base), `superseded` (a newer round) and `invalid_input` accept nothing. For `saved`, `error` or `blocked`, restore the condition (task branch, clean tree, tracker access) and run `workflow review-result ID --round=ROUND --reconcile`: no model call, no attempt. `review-result` names `result_path` (the full answer) and `stream_path` (raw provider streams, kept until the task is Done). Read streams only to diagnose INCONCLUSIVE, a failure or a disputed result. Never copy private answers or streams into the tracker or public output, edit workflow state or restore refs to revive acceptance.
8. Verify each finding against code and requirements. Reject taste-only, quota-driven or hypothetical blockers; a complexity finding needs a location, a real cost and a simpler behavior-preserving alternative. Journal valid findings in task language, uncheck only contradicted items, resume with `tracker claim ID --resume`, then fix, commit, validate and review sequentially within budget. Push back with evidence, escalate material disagreement or no progress, and never self-award PASS.
9. For already-integrated parent recovery the round asks for review of the complete implementation from requirements, code and Git history; an empty diff is not acceptance and unclear scope is INCONCLUSIVE. `workflow approve ID --reason TEXT` records the user's explicit acceptance of the current head, never a verdict. GitHub cloud review is requested by ab-land.
