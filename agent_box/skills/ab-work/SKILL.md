# ab-work

1. Read `tracker get ID`, related history, repository guidance, and `tracker ready`. Resolve ambiguity with ab-interview. Read `config show` for the effective configuration and its source; inside a container host/default `load_config` is not the workflow configuration. Only the coordinator calls `workflow begin ID --primary PROVIDER`; inspect its reported merge mode, and use --resume only after inspecting an interrupted task and its branch. Branch names follow the task ID and the base branch is origin's live default; neither is configured or recorded anywhere. A branch already pushed for the task is adopted, in a fresh clone too; ambiguous or diverged branches stop instead.
2. Work on one implementation task at a time. A tiny task may be implemented directly by the primary. Otherwise `workflow prepare ID --role worker --primary PROVIDER` selects model/effort from workflow.tiers. Before native delegation, compare the available role, provider, model and effort with the exact allowed candidate, require its native_profile_ready, and ensure the tool enforces those settings. A role name alone proves nothing; if settings are unsupported or unknown, use `workflow run ID --role worker --primary PROVIDER --brief FILE`. Never launch nested agent-box sessions. Do not reschedule an active worker based on changing usage.
3. Handoff in English: task ID, bounded scope, relevant paths, decisions, validation, and expected report. Pass the `repository_instructions` that `prepare` returns to the delegate. A worker changes project files in the working tree and returns a report; it never commits, pushes, switches branches, writes the tracker or touches GitHub, and it never edits `.agent-box.json`. Progress and evidence belong in the report: you decide what to record afterwards. Keep the `handoff` descriptor to yourself; it names one delegation, bound to its repository, tracker project, task, scope, role and tier, so each delegation needs its own `prepare`. Accepting a worker report drops any earlier validation and review acceptance, and is refused if the branch or HEAD moved meanwhile. For native reports use `workflow report ID --role worker --primary PROVIDER --provider ACTUAL_PROVIDER --model ACTUAL_MODEL --effort ACTUAL_EFFORT --scope SCOPE --handoff DESCRIPTOR --file FILE`. Add `--fallback-reason REASON` for a fallback candidate, explaining why the preferred route could not run. Exact route checks precede acceptance changes; never substitute configured values for unknown actual settings. CLI reports are checked and recorded automatically.
4. Investigate failures before fixes: reproduce, trace evidence to the cause, test one hypothesis. When a regression test adds value, show it fails for the intended reason, fix minimally, run relevant validation. Reuse code; avoid speculative frameworks and redundant tests.
5. New dependencies, contradictions or overlap with future work require the user's decision; update all affected tasks and relations. Provider errors require inspecting side effects before retrying; never silently restart a partially completed worker.
6. Primary reviews the worker's evidence for completeness, records task-language progress and checks acceptance items in the tracker itself, commits the implementation, then runs `workflow validate ID -- COMMAND ARGS`. Read `workflow inspect ID` for the current scope, effective route and exact review triggers. For direct-primary changes record `workflow writer ID --provider ACTUAL` before review, including resumed fixes. This is mechanical validation, not independent code review. Use ab-review according to configured policy. For a local parent only, explicit user acceptance of the inspected result may instead be recorded with `workflow approve ID --scope DIGEST --reason TEXT`; a request to avoid subagents is not acceptance. Never invent independent PASS, call the tracker adapter directly, or merge manually to bypass a refusal.
7. On review findings, post a task-language summary, uncheck only contradicted items and return to Doing; fix sequentially, commit and validate/review again. Never invent reviewer PASS. Keep loops within max_rounds; stop for ambiguity or no progress.
8. `workflow finish ID` integrates a completed subtask into the parent and marks it Done; configured auto-push publishes only the parent in GitHub merge mode and publishes nothing in local mode. Repeat with the next ready subtask. Validate/review the complete parent diff, then finish the parent to Review. Follow the reported route: offer ab-pr in GitHub mode or use ab-land for a local fast-forward. Parent Done requires proven integration into the base.
