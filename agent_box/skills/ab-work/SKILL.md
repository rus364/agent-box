# ab-work

1. Read the task with `tracker get REFERENCE` (user number, title, URL or ID) per ab-tracker; use its canonical `id` unchanged throughout workflow. Read applicable repository guidance and only relevant related history. Use `tracker ready` when selecting work, not after an exact ID is already chosen. Use `config show` when diagnosing configuration; `workflow inspect ID` is authoritative for the task's effective source, branch, acceptance and review budget. Only the coordinator calls `workflow begin ID`; inspect its merge mode. Resume only after inspecting interrupted ownership and branch state. Stop on ambiguous or diverged task branches.
2. Work on one implementation task at a time. Make small bounded edits yourself: commit, then validate; nothing else is recorded. For a separate implementation assignment or a bounded research question that would otherwise need substantial reading, either spawn a native subagent (profile `ab-worker` or `ab-scout` sets the model) or run `workflow delegate ID --role worker|scout --brief FILE`, which starts the role's first available configured candidate as a managed CLI and prints its Markdown answer (Done / Evidence / Limitations), or on failure each category with a diagnostic path. The brief is a compact English file outside the tree: goal, scope and relevant paths, decisions and limitations, and for a scout its one question. Give every assignment a fresh agent and never pass it conversation, tracker comments or other agents' history. Scouts only read and may overlap up to `workflow.scout.limit`; a worker changes only project files on the task branch. Only you commit, switch branches or write the tracker and GitHub: verify the answer against the code, commit what you accept and revert the rest. Never stash, reset or adopt unrelated changes.
3. Investigate failures before fixes: reproduce, trace the cause, test one hypothesis. Useful regressions must fail for the intended reason. Check actual consumers/requirements; prefer local fixes or reuse. Justify why smaller changes cannot suffice before redesign; preserve required error/safety/compatibility checks. Avoid needless layers, duplicated state/checks, speculative generalization and tests restating implementation.
4. Ask the user about material unresolved dependency, contradiction or scope alternatives. Once decided, update affected tasks/relations without seeking duplicate approval.
5. Before the final implementation commit or any review dispatch, read `tracker checklist ID` and match every acceptance/validation item to evidence from the actual result. Resolve missing work first; assign cross-task integration criteria to the correct task before implementation, preserving requirements. Never check an item merely to pass a gate; an item only the user can close stays open and blocks a subtask's finish and every landing, not the round and not the parent's move to Review. Record task-language progress and evidenced checklist items, commit the implementation, then run `workflow validate ID -- COMMAND ARGS`. Read `workflow inspect ID` for the current scope, effective route, exact review triggers and the one `next_step` this head's record calls for. This is mechanical validation, not independent code review. Use ab-review: configured provider first; fallback only after observed unavailability. Explicit user acceptance of the current head may instead be recorded for any task in either mode with `workflow approve ID --reason TEXT`; a request to avoid subagents is not acceptance. Validation, review and approval belong to the head and base: a new commit retires them, task edits do not. Never invent independent PASS, call the tracker adapter directly, or merge manually to bypass a refusal.
6. Verify findings against code/requirements and ab-review's proportionality rules. Push back with evidence; escalate material disagreement without self-awarding PASS. Journal valid findings in task language, uncheck only contradicted items and return to Doing. Fix directly or with a fresh worker. Commit, validate and review sequentially. Budget, failures and any additional allowance follow ab-review.
7. `workflow finish ID` integrates a completed subtask into the parent, marks it Done and, where branch cleanup is enabled, releases the subtask's branch once the parent branch contains its head; configured auto-push publishes only the parent in GitHub merge mode and publishes no task branches in local mode. Local ab-land publishes the accepted base after fast-forward when auto_push is enabled (the default within opt-in workflow). Repeat with the next ready subtask. Validate/review the complete parent diff, then finish the parent to Review. Follow the reported route without asking: ab-pr in GitHub mode, then ab-land; ab-land alone for a local fast-forward. Ask the user only about a blocker or disputed scope. Parent Done requires proven integration into the base.

A completed reviewer response has a separate reconciliation status. Before rerunning after an application error, use `workflow review-result ID --round=ROUND` and read its private `result_path`; `--reconcile` retries without another model call or attempt. Follow ab-review recovery rules; a historical verdict alone is not current acceptance.
