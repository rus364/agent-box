# ab-work

1. Read `tracker get ID`, applicable repository guidance and only relevant related history. Use `tracker ready` when selecting work, not after an exact ID is already chosen. Use `config show` when diagnosing configuration; `workflow inspect ID` is authoritative for the task's effective source, branch, acceptance and review budget. Only the coordinator calls `workflow begin ID --primary PROVIDER`; inspect its merge mode. Resume only after inspecting interrupted ownership and branch state. Stop on ambiguous or diverged task branches.
2. Consider scouts only for distinct bounded unanswered questions that materially affect a decision or avoid substantial repeated reading. Quick lookup stays with the coordinator; duplicate scouts are prohibited. Only the coordinator dispatches scouts, never workers or scouts. Prepare each with `workflow prepare TASK --role scout --tier 0 --primary PROVIDER --question "ONE QUESTION" --brief FILE`; keep the question separate from Goal/Acceptance/Validation. Pass `delegate_handoff` unchanged as the complete initial bootstrap to a fresh read-only agent. It references the canonical read-only input by path and SHA-256; never inline or reconstruct it. Several scouts may overlap up to effective `scout_limit`: managed runs enforce shared repository slots; native launches are coordinator-counted because CLI processes cannot own native subagent leases. Consume the prepared `managed_command` or native `report_command`; never reschedule. Reports contain English facts, source locations and uncertainty, not reviewer verdicts. Work on one implementation task at a time. In auto policy, explicitly choose `workflow prepare ID --role worker --primary PROVIDER --execution direct --reason "Small bounded edit"` or `--execution delegated --reason "Separate implementation assignment" --brief FILE`; forced direct/delegated policies determine the choice and reject contradictions. The returned action, route, context policy and instructions are authoritative. `work-in-current-session` means implement directly without changing or inventing model/effort/tier. A delegated route prefers native when the live interface satisfies the prepared facts and common contract; otherwise use the returned `managed_command` (`workflow run ID --handoff DESCRIPTOR --brief FILE`, repeating a supplied `--tier`). Inspect `execution` for the bound policy, choice, reason and model source. Do not infer capabilities from profile names or reschedule an active worker because usage/configuration changed. Auto allows only direct-to-delegated escalation: before edits or after a coordinator checkpoint commit, repeat prepare with `--execution delegated --reason TEXT --brief FILE`. Dirty escalation refuses without changing files; never stash, reset or adopt unrelated changes. The previous descriptor becomes stale.
3. For delegation, write one compact UTF-8 English `--brief FILE` outside the tree with current Goal/Acceptance/Validation, scope, paths, decisions and limitations. Pass `delegate_handoff` unchanged as the complete initial message; its bootstrap references the complete read-only input by path and SHA-256. Never inline or rewrite that input. Ingest native output with the returned `report_command`. Each new assignment and completed-worker follow-up gets a fresh worker; clarifications and ordinary edits stay with the active worker. Never reuse a completed agent or import conversation, comments or agent history. A worker changes only project files and returns the English schema; the coordinator alone handles commits, branches, tracker and GitHub. Inspect provider failures before retrying. Accept only a report matching the prepared descriptor, scope and actual route.
4. Investigate failures before fixes: reproduce, trace the cause, test one hypothesis. Useful regressions must fail for the intended reason. Check actual consumers/requirements; prefer local fixes or reuse. Justify why smaller changes cannot suffice before redesign; preserve required error/safety/compatibility checks. Avoid needless layers, duplicated state/checks, speculative generalization and tests restating implementation.
5. Ask the user about material unresolved dependency, contradiction or scope alternatives. Once decided, update affected tasks/relations without seeking duplicate approval.
6. Primary reviews the worker's evidence for completeness, records task-language progress and checks acceptance items in the tracker itself, commits the implementation, then runs `workflow validate ID -- COMMAND ARGS`. Read `workflow inspect ID` for the current scope, effective route and exact review triggers. For direct changes, ingest the prepared report before committing so its HEAD still matches; `workflow writer ID --provider ACTUAL` records writer identity but does not complete a prepared execution. This is mechanical validation, not independent code review. Use ab-review according to configured policy. For a local parent only, explicit user acceptance of the inspected result may instead be recorded with `workflow approve ID --scope DIGEST --reason TEXT`; a request to avoid subagents is not acceptance. Never invent independent PASS, call the tracker adapter directly, or merge manually to bypass a refusal.
7. Verify findings against code/requirements and ab-review's proportionality rules. Push back with evidence; escalate material disagreement without self-awarding PASS. Journal valid findings in task language, uncheck only contradicted items and return to Doing. Follow the prepared worker action: direct work stays in the current session; a delegated fix gets a fresh worker. Commit, validate and review sequentially. Attempts remain spent across failures and scope changes; only ab-review's explicit user allowance raises the budget.
8. `workflow finish ID` integrates a completed subtask into the parent and marks it Done; configured auto-push publishes only the parent in GitHub merge mode and publishes no task branches in local mode. Local ab-land publishes the accepted base after fast-forward when auto_push is enabled (the default within opt-in workflow). Repeat with the next ready subtask. Validate/review the complete parent diff, then finish the parent to Review. Follow the reported route: offer ab-pr in GitHub mode or use ab-land for a local fast-forward. Parent Done requires proven integration into the base.

The coordinator may select concise evidence for a delegated worker using `--facts FILE` at prepare and the same file at managed run. JSON contains exact `task`, current `scope`, and 1–12 `facts`, each with `text`, 1–6 `sources` and optional `limitations` (16 KiB total; strings limited to 1000/300/500 characters respectively). Strict keys/types apply. These selected facts reduce repeated reading/context without promising token savings. Never pass raw scout output, conversations, comments or agent history. Reviewer requirements remain independent.
